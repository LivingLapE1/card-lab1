# Review 지침 — Fun English 웹 UI 골격

> 담당: Review 서브에이전트 (Build와 다른 에이전트, opus, 추론 강도 xhigh)
> 근거: 승인된 `spec.md`, Build가 만든 파일들

## 1. 목표

Build가 만든 웹 앱이 **spec대로 정상 동작하는지**, **코드에 문제가 없는지** 독립적으로 검증하고 결과를 `review.md`에 쓴다.
Build의 보고를 믿지 말고 직접 확인한다.

## 2. 수정 범위 (꼭 지킬 것)

- **만들거나 고칠 수 있는 파일: 프로젝트 루트의 `review.md` 하나뿐.**
- 앱 코드(`index.html`, `css/`, `js/`, `assets/`, `README.md`, `.nojekyll`, `.gitignore`)는 읽기만 한다. 문제를 찾아도 직접 고치지 않는다. 고치는 일은 Build가 한다.
- `design/`, `instructions/`, `CLAUDE.md`, `spec.md`도 고치지 않는다.
- git 커밋·푸시를 하지 않는다.

## 3. 먼저 읽을 것

1. `spec.md` — 특히 5장(라우팅), 7장(화면별), 8장(데이터), 9장(접근성·반응형·움직임), 11장(검증 목록 A–I)
2. `design/DESIGN.md`, `design/mockup.html` — 디자인 일치 확인용
3. `CLAUDE.md`
4. Build가 만든 파일 전부

## 4. 확인 방법 (이 컴퓨터 사정)

바탕화면 폴더에서 띄운 로컬 서버는 macOS 개인정보 보호 때문에 파일을 못 읽는다. **임시 폴더에 복사해서 띄운다.** 임시 폴더 위치는 작업 요청 메시지에 있다.

```bash
rsync -a --delete --exclude .git "<프로젝트 폴더>/" "<임시 폴더>/review-site/"
cd "<임시 폴더>" && python3 -m http.server 8702 --bind 127.0.0.1 --directory "<임시 폴더>/review-site"
```

- 서버는 백그라운드로 실행하고, 끝나면 반드시 끈다.
- 브라우저 도구로 `http://localhost:8702/`을 열어 실제로 눌러 보고, 폭을 360 / 768 / 1280px로 바꿔 본다. 콘솔 오류도 본다.
- 코드는 직접 읽어서 본다: 데이터 한 겹 규칙(화면이 `js/services/index.js`만 쓰는지, 화면 코드에 `localStorage`·`sessionStorage`·`fetch`가 없는지), 넣는 값 이스케이프, 정리 함수, 경로가 모두 상대 경로인지, 비밀값·실제 이름이 없는지.
- `node --check`로 자바스크립트 문법을 확인한다.

## 5. 검증할 것

1. spec 11장 검증 목록 A–I를 **하나도 빠짐없이** 확인한다. 항목마다 통과 / 실패 / 확인 못 함(이유)을 적는다.
2. 그 밖에 코드를 읽다가 발견한 문제(버그, 접근성, 보안, 성능, 유지보수)를 적는다.
3. 시안(`design/mockup.html`)과 나란히 놓고 모양이 크게 다른 곳이 있으면 적는다. spec 13장에 적힌 "달라지는 점"은 문제가 아니다.

## 6. review.md 형식 (한국어)

```markdown
# review.md — Fun English 웹 UI 골격
> 검증: Review 서브에이전트 · 날짜 · 확인 환경(브라우저, 폭)

## 요약
- 결과: 통과 / 고칠 것 있음
- 실패 n개 (반드시 고칠 것 a개, 고치면 좋은 것 b개), 확인 못 함 c개

## 반드시 고칠 것
| # | 어디(파일:줄) | 무엇이 문제인가 | 어떻게 재현하나 | 고치는 방향 |

## 고치면 좋은 것
(같은 표)

## 검증 목록 결과 (spec 11장)
### A. 구조·배포 … I. 디자인 일치
- [x] 항목 — 통과
- [ ] 항목 — 실패: 이유 (위 표 # 번호)
- [?] 항목 — 확인 못 함: 이유

## 확인 못 한 것
```

"반드시 고칠 것"은 spec과 다르게 동작하거나, 화면이 깨지거나, 오류가 나거나, 접근성·보안 기준을 어기는 것이다. 취향 차이는 "고치면 좋은 것"에 둔다.

## 7. 다시 검증할 때

Build가 고친 뒤 다시 검증을 맡으면, 지난 review.md의 실패 항목을 하나씩 다시 확인하고 결과를 갱신한다. 고치면서 다른 곳이 깨지지 않았는지도 본다.

## 8. 끝나면 보고할 것 (짧게)

결과(통과 / 고칠 것 있음), 반드시 고칠 것 목록(한 줄씩), 확인 못 한 것.

# Plan 지침 — Fun English 웹 UI 골격

> 담당: Plan 서브에이전트 (opus, 추론 강도 xhigh)
> 결과물: 프로젝트 루트의 `spec.md` 한 개

## 1. 목표

사용자가 승인한 디자인(Fun English, 볼드 레트로) 그대로 **실제 웹 앱의 화면 골격**을 만들기 위한 계획을 세운다.
이번 단계는 **디자인된 화면을 웹으로 구성하는 것까지**다. 기능(진짜 로그인, 데이터베이스, 게임 로직)은 다음 단계에서 따로 한다.

Build 서브에이전트가 `spec.md`만 읽고 바로 만들 수 있을 만큼 구체적으로 쓴다.

## 2. 수정 범위 (꼭 지킬 것)

- **만들거나 고칠 수 있는 파일: 프로젝트 루트의 `spec.md` 하나뿐.**
- 다른 파일은 읽기만 한다. 코드 파일을 만들지 않는다.
- git 커밋·푸시를 하지 않는다.

## 3. 먼저 읽을 것

1. `CLAUDE.md` — 프로젝트 규칙, 게임 4종, 화면 구성, 공통 기능, 확정된 UI 디자인
2. `design/DESIGN.md` — 색·글꼴·간격·그림자 토큰, 그림 체계, 움직임, 접근성, 하지 않을 것
3. `design/mockup.html` — 승인된 클릭형 시안 (화면 5개: 인트로, 학생 로그인, 교사 로그인, 게임 선택, 교사 대시보드). 마크업·CSS·SVG·JS를 자세히 본다.
4. 스타일 스킬 파일 2개 (위치는 작업 요청 메시지에 적혀 있다): `ui-design-foundation`, `ui-style-bold-retro`

## 4. 이번 단계에 넣을 것 / 뺄 것

넣을 것:
- 시안의 화면 5개를 실제 앱 구조로 옮기기 (같은 모양, 같은 토큰, 같은 흐름)
- 화면 사이 이동(라우팅), 뒤로 가기, 새로고침해도 같은 화면 유지
- 게임 4종 각각의 **자리 화면**(게임 선택 → START를 누르면 들어가는 화면). 게임 판은 아직 만들지 않고, 같은 디자인으로 "곧 열려요" 상태와 돌아가기만 둔다. 어떻게 보일지 spec에 정한다.
- 시안처럼 가짜(목업) 데이터로 채운 화면. 가짜 데이터는 한곳에 모아, 나중에 진짜 데이터로 바꾸기 쉽게 한다.
- 시안에 있던 화면 상태: 기본, 올림, 누름, 포커스, 오류(빈 칸 로그인), 로딩(구글 버튼), 빈 상태(기록 없음)
- 반응형(360 / 768 / 1280px), 접근성, 움직임 줄이기

뺄 것 (다음 단계):
- 진짜 구글 로그인, 아이디·비밀번호 확인, 세션 유지
- 데이터베이스, 학습 기록 저장, 교사 대시보드의 진짜 집계
- 게임 4종의 실제 게임 로직
- 학생 아이디 생성·관리 화면 (시안에서도 "다음 시안"으로 남겨 둠. 버튼만 두고 안내를 띄운다)

## 5. 제약

- **GitHub Pages(정적 호스팅)** 에서 그대로 동작해야 한다. 저장소: `eversunk2-tech/card-lab1`, `main` 브랜치 루트를 Pages로 내보내는 중. 앱은 사이트 첫 주소(`/card-lab1/`)에서 열리게 한다.
- **공개 저장소**다. 비밀값(API 키, 비밀번호)을 넣을 자리를 만들지 말고, 나중에 넣을 때도 저장소에 들어가지 않게 하는 방법을 spec에 한 줄 적는다.
- **데이터베이스·백엔드는 정하지 않는다** (CLAUDE.md 규칙: 사용자에게 묻고 정한다). 대신 나중에 어떤 백엔드든 붙일 수 있도록, 화면 코드가 데이터·인증을 직접 다루지 않고 한 겹(예: 데이터 접근 모듈)을 거치게 설계한다.
- `design/DESIGN.md`의 토큰과 "하지 않을 것"을 지킨다. 시안과 다른 점이 생기면 이유와 함께 spec에 적는다.
- `design/mockup.html`과 `design/DESIGN.md`는 참고 자료로 그대로 둔다.
- 외부 라이브러리는 꼭 필요할 때만. 쓰면 이유를 적는다.
- 글꼴은 시안처럼 Google Fonts(Gasoek One, Silkscreen, IBM Plex Sans KR).

## 6. 정해야 할 것 (추천 + 이유 + 대안)

아래는 spec에 **추천안과 대안**을 함께 적고, "사용자 승인 필요"로 표시한다.

1. 프런트엔드 방식: 빌드 없는 HTML/CSS/JS(ES 모듈)로 할지, 빌드 도구(예: Vite)와 GitHub Actions 배포를 쓸지. 초등학교 수업용, GitHub Pages, 나중에 붙을 백엔드, 유지보수 쉬움을 기준으로 판단한다.
2. 라우팅 방식: 해시 라우팅(`#/select`) 또는 여러 HTML 페이지 등. GitHub Pages에서 새로고침·직접 접속이 깨지지 않는 쪽.
3. 게임 자리 화면의 모양과 문구.
4. 그 밖에 Build 전에 사용자가 골라야 하는 것이 있으면 모두.

## 7. spec.md 목차 (한국어로 작성)

1. 한 줄 요약
2. 이번 단계 범위 — 넣을 것 / 뺄 것
3. 기술 방식 — 추천안, 이유, 대안 (사용자 승인 필요 표시)
4. 파일 구조 — 트리와 파일마다 역할 한 줄
5. 라우팅 — 주소 목록, 화면 간 이동, 없는 주소 처리
6. 공통 요소 — 토큰(CSS 변수), 창(`.win`), 버튼, 스티커, 입력 칸, 스위치, 토스트, SVG 그림 모음, 상단 바들. DESIGN.md와 어떻게 연결되는지
7. 화면별 명세 — 인트로 / 학생 로그인 / 교사 로그인 / 게임 선택 / 게임 자리 화면 4종 / 교사 대시보드. 화면마다 구성 요소, 상태, 가짜 데이터, 이동, 반응형 동작
8. 데이터 모양 — 가짜 데이터 구조(학생, 교사, 게임, 기록, 단어). 나중에 DB로 옮기기 쉬운 형태로. 데이터 접근 모듈의 함수 목록(이름, 입력, 출력)
9. 접근성·반응형·움직임 기준
10. Build 작업 순서 — 단계별 할 일
11. Review 검증 목록 — Review 서브에이전트가 하나씩 확인할 수 있는 수용 기준 (예: "360px에서 가로 스크롤 없음", "새로고침해도 같은 화면")
12. 사용자가 정할 것 — 번호를 매긴 질문 목록
13. 시안과 달라지는 점

## 8. 끝나면

작업 요청 메시지에 답할 때, spec.md를 썼다는 것과 **사용자가 정할 것** 목록, 추천안을 짧게 정리해 돌려준다. spec 전문을 붙여 넣지 않는다.
